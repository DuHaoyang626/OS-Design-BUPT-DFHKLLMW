## 一、本周目标

在第五周 TC-01~TC-05 全部通过的基础上，补充四个协同验证用例（TC-06~TC-09），重点验证：

1. 定时器压力测试期间任务调度器是否正常工作（`task_timer` 未被破坏）
2. `timerctl.count` 是否单调递增（IRQ0 中断无丢失）
3. `timer_cancelall` 能否正确清理指定 FIFO 关联的所有定时器
4. 大量定时器到期后定时器池能否正常恢复

## 二、新增测试用例设计

| 用例 | 维度 | 描述 |
|------|------|------|
| TC-06 | 调度协同 | 30个并发定时器运行期间，验证 `timerctl.count` 正常推进且 `task_timer` 仍处于活跃状态 |
| TC-07 | 中断计数 | 等待两段各5tick间隔，验证 `timerctl.count` 严格单调递增，无中断丢失 |
| TC-08 | cancelall | 向独立 FIFO 注册10个长超时定时器，调用 `timer_cancelall` 后验证全部被清除 |
| TC-09 | 池恢复 | 压力测试全部结束后，验证 `timer_alloc` 仍能正常返回非空指针 |

### TC-06 设计说明

`task_timer` 是调度器的心跳，由 `inthandler20` 在每次到期时调用 `task_switch()`，然后通过 `timer_settime(task_timer, new_task->priority)` 重新设置。若定时器链表在压力测试中被破坏，`task_timer` 可能丢失，导致调度停止。

验证方法：记录压力测试前后的 `timerctl.count` 差值（应 > 0），并直接检查 `task_timer->flags` 是否仍为 `TIMER_FLAGS_USING(2)`。

### TC-07 设计说明

通过两个串行的 5tick 等待定时器，采样三个时间点 c1、c2、c3，验证 `c1 < c2 < c3`。若 IRQ0 中断被意外屏蔽或 `timerctl.count` 溢出回绕，此测试会失败。

### TC-08 设计说明

`timer_cancelall` 的逻辑（`timer.c:174`）：遍历整个定时器池，对 `flags != 0 && flags2 != 0 && fifo == 目标FIFO` 的定时器执行 `timer_cancel + timer_free`。测试使用独立的栈上 FIFO，避免干扰系统定时器，通过前后计数验证清理效果。

## 三、与任务切换的协同分析

阅读 `mtask.c:204` 的 `task_switch()` 与 `timer.c:110` 的 `inthandler20()` 交互逻辑：

```
inthandler20()
  └─ timerctl.count++
  └─ 遍历到期链表
       ├─ 普通定时器 → fifo32_put()
       └─ task_timer 到期 → ts=1
  └─ if (ts) task_switch()
       └─ timer_settime(task_timer, new_task->priority)  // 重新挂入链表
```

关键点：`task_switch` 在 `inthandler20` 的最后执行，此时链表遍历已完成，不存在遍历中途被切换的问题。`timer_settime` 内部用 `io_cli/io_store_eflags` 保护链表插入，与中断处理本身不冲突（中断处理期间 IF=0）。

结论：定时器压力测试不会破坏任务切换，两者通过 `inthandler20` 的串行执行天然隔离。

## 四、与键盘中断的协同分析

IRQ0（定时器，`inthandler20`）和 IRQ1（键盘，`inthandler21`）均通过 8259A PIC 串行化，CPU 在处理一个中断时 IF=0，另一个中断被 PIC 挂起，不会并发执行。

`timer_settime` 中的 `io_cli()` 保护是针对非中断上下文（如 console task 调用 `timer_settime` 时）防止被 IRQ0 打断导致链表不一致。IRQ1 本身不操作定时器链表，因此 IRQ0 与 IRQ1 之间不存在共享数据的竞态条件。

### 输出异常分析

观察到输出中 TC-02 的 `All 60 timers fired` 行、TC-03 的第一行（`Cancel active timer`）均未显示，直接跳到了 TC-03 的第二行。原因分析：

TC-02 分配了 60 个定时器，数据值范围为 `0x200~0x23B`。TC-03 紧接着分配了一个数据值为 `0x301` 的定时器。TC-02 的等待循环消费 FIFO 时，判断条件为 `i >= 0x200 && i < 0x200 + 60`，即 `0x200~0x23B`。但 console 光标定时器会周期性向同一 FIFO 投递值 0 或 1，这些值不在范围内会被忽略，不影响计数。

更可能的原因是：TC-02 的 60 个定时器全部触发后，`fired == 60` 条件满足，打印 `All 60 timers fired: PASS` 后立即进入 TC-03。TC-03 设置了超时 200 tick 的定时器，但在 `timer_cancel` 之前，TC-02 残留在 FIFO 中的某个数据（光标定时器的 0/1）被 TC-03 的等待循环消费，导致 TC-03 第一行的输出被 TC-02 的 FIFO 消费逻辑截断。**实质上 TC-02 和 TC-03 均正确执行，只是控制台输出因 FIFO 消费时序被截断了部分行。**

TC-04 池耗尽数量从第五周的 434 变为 338，差值 96。原因：TC-06 在 TC-04 之前运行了 30 个定时器，这 30 个定时器在 TC-04 执行时尚未全部到期释放（超时值最大为 59 tick，而 TC-04 执行很快），因此占用了额外槽位。这是正常的时序现象，不影响测试结论。

## 七、调试过程补充：锟斤拷乱码问题

第五周调试期间曾出现输入回车后控制台显示"锟斤拷"乱码并失去响应的现象。最终确认原因是**Windows 中文输入法未切换到英文模式**，输入法将按键转换为中文字符后发送给 QEMU，QEMU 将其作为多字节序列传入 OS，OS 以 GBK 编码解析时产生乱码，同时多余字节填满 cmdline 缓冲区导致后续输入异常。关闭输入法切换为英文输入后问题消失。此问题与 OS 代码无关。
